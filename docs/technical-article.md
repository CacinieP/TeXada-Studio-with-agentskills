# 用 Agent Skills 构建可审阅的 LaTeX 修复工作流

作者：LinguistsWantTech 团队  
队长：邓一纯　队员：刘丰华

项目：TeXada Studio with Agent Skills  
投稿类型：第三届 NVIDIA DGX Spark Hackathon 参赛技术征文  
代码：https://github.com/CacinieP/TeXada-Studio-with-agentskills

一份 LaTeX 报表能够编译成 PDF，不代表里面的数字正确。我们准备的合成样本中，两行利润分别是 45 和 60，合计却写成了 115。排版引擎会忠实地把 115 印在页面上。另一份公式样本写着不完整的下标 `a_`，即使模型补成了 `a_1`，检查器也无法知道原作者想写的是 1、n，还是另一个符号。

这两个例子决定了 TeXada 的设计：把检查、候选生成、编译和人工确认分开。我们的目标是让使用者知道改了哪里、依据是什么，以及哪些判断仍然需要自己完成。

## 先把判断拆开

当前版本接受单个 `.tex` 文件，在浏览器里提供源码编辑、第一页预览、问题定位和修复对比。它检查部分行内公式语法，以及简单 `tabular` 表格的合计。对于语法错误，节点内的模型提出候选，SymPy 再检查候选能否解析；对于符合约定的合计行，程序根据数据行重新计算。

这些结果具有不同含义。SymPy 接受表达式，是语法层面的结果；Tectonic 生成 PDF，是编译层面的结果；一处修改是否保留原文含义，仍然需要来源证据和人工判断。我们因此没有用一个“修复成功率”把三种结果合并，也没有把演示样本的表现当成真实 OCR 数据集的准确率。

## Skills 需要写清输入和失败路径

仓库把专业步骤组织成 `SKILL.md` 与脚本。Agent Skills 规范规定了 `name`、`description` 等元数据，并建议把细节按需放入资源文件。我们用这种结构说明何时检查公式、怎样读取表格节点、如何生成报告，而把具体计算交给 Python 工具。[Agent Skills 规范](https://agentskills.io/specification)

目前，CLI harness 按节点类型执行预先编排的流程：读取已有 `layout.json`，检查节点，必要时请求最多两次修复，再写入 `state.jsonl`。下次使用相同输入和状态目录运行，会跳过已经完成的节点。Studio 是另一条交互路径，通过 FastAPI 连接浏览器、检查脚本、模型与编译器。它没有动态加载所有 Skill 正文，也没有通用的自主工具规划器。

整理参赛材料时，我们发现旧说明中仍有尚未实现的设计：自动版面解析、图像重裁剪、多模型调度和十几路并发。我们把这些表述移出了“当前能力”。`doc-layout-parse` 现在明确说明它负责已有结构树输入的准备约定；仓库并不存在可直接运行的 PDF/OCR 解析器。对使用者来说，知道输入前提比看到更长的功能清单有用。

## 不让检查失败变成绿色通过

工程检查发现，Studio 原先在无法解析检查器输出时，会回退成 `OK`。这会把依赖缺失、进程失败甚至异常输出伪装成文档没有问题。我们改为 `NEEDS_ENV`，保留原文，阻止这类故障继续调用模型。回归测试覆盖了非 JSON 输出、异常退出和超时。

另一个细节来自 SymPy。默认的 LaTeX 解析在某些情况下会接受输入的一部分，例如本地测试中 `x+` 被解析为 `x`。我们增加严格检查，避免把尾部残缺公式当作通过。与此同时，ANTLR 的严格起止位置检查会把带 `\left` 和 `\right` 的合法表达式误拒绝，因此先检查原始定界符，再去掉尺寸命令做完整解析，并用正反例固定行为。SymPy 文档也把 LaTeX 解析标为实验性功能，这一层不能替代完整 TeX 编译。[SymPy 解析文档](https://docs.sympy.org/latest/modules/parsing.html)

这些修改没有提高模型的知识能力，但改善了整个系统向使用者传达结果的可靠性。

## 用负例约束“修好”的含义

补充案例时，我们没有只增加更多成功演示，而是整理了 27 个可以直接执行的合成输入：10 个公式、17 个表格，分成 24 个契约案例和 3 个语义边界案例。运行器逐例保存输入、预期、原始响应、退出码与检查脚本摘要；本轮 27 个案例都符合各自预期，但运行没有调用模型，因此这个数不能称为模型准确率。[案例定义与复现](../samples/evaluation/README.md)

其中 `1+1=3` 的预期就是语法 `OK`，因为我们的工具没有证明等式的职责。百分比混合和会计括号则应被拒绝，不能抽取其中的数字直接求和。这样的案例能帮助用户辨认“没有发现问题”和“已经证明正确”的区别。

负例也找到真正的实现错误。合计单元格是横杠时，旧程序能够记录一处修复，却没有改动源码；现在它转人工，修改数保持为零。另一个问题是大整数求和：即使使用 Decimal，默认的 28 位精度也可能让一个少 1 的合计通过。我们按输入位数设置精度，并保留正确和错误的大整数两例防止回退。CLI 表格事件也增加原始网格与候选网格，报告从“重提取”的文字说明变为可以核对的真实差异。

三个新增 Studio 文档分别演示正常对照、数学语义反例和必须人工处理的表格。回归使用真实本地检查器，并拦截任何模型调用，确认这些场景没有自动改写原文。完整调用关系、失败路径、已知限制和证据分层放在 [Skills 技术报告](skills-technical-report.md)，逐步操作见 [案例手册](casebook.md)。

## Monaco 的问题要沿资源链排查

编辑器的可用性不只取决于页面上的一段 JavaScript。Monaco 还依赖模块、样式、字体和 Worker 资源。我们将 0.52.2 版本的完整资源固定在仓库中，保留上游 MIT 许可证与摘要清单，通过本站路径提供服务。受限 Cookie 为静态资源提供认证，API 继续单独校验 token。浏览器验收检查了实际加载、页面错误与请求来源。[Monaco 上游仓库](https://github.com/microsoft/monaco-editor)

界面上，缺失的隐藏样式曾让尚未使用的 diff 区域占据空间；切换文档时没有完整销毁 diff 模型，也会留下旧状态。我们补齐隐藏与折叠规则、模型释放和异步结果过期检查。修复完成后先进入左右对比，使用者点击“采用候选到编辑器”，源码、预览和导出内容才保持一致。任务报错后，按钮也必须恢复可用，不能让界面停在“修复中”。

最终导出的质检报告记录行号、修改前后内容、输入与候选的 SHA256、编译结果和模型标签。哈希用于识别这次处理的具体内容，不是对文档正确性的背书。

## Spark 实机验证了什么

早前录屏演示运行在分配的 ARM64 Spark 节点，GPU 查询结果为 NVIDIA GB10。Ollama 返回的模型标签是 `qwen3.8:27b-q4_K_M`；这是部署环境中的标签，我们没有据此扩展声明模型的官方架构或视觉能力。当时请求只包含文本，没有传入页面图像，也不通过 MCP 调用内容服务。本轮新增案例在本机执行检查器，未重跑真实模型或编译，不能替代旧视频的运行条件。

演示分别展示报表合计修复和公式候选修复。报表中 115 被重算为 105；公式示例保留逐处差异，并展示修复前后的编译结果。独立 CLI fixture 用于验证状态机和断点续跑，其报告明确标注为测试替身；这些 fixture 结果不能计入模型效果评估。具体运行记录随项目报告提供。

我们没有用统一内存容量推算十几路并发吞吐，也没有做消费级 GPU 对照试验。当前能够证明的是：模型推理与文档工具在同一节点完成了这条工作流。运行期间，浏览器编辑器资源来自本站；Tectonic 初始包下载、模型安装和旧仪表盘依赖仍可能需要网络，因此不宣称全流程断网可用。[Tectonic 项目说明](https://tectonic-typesetting.github.io/en-US/)

## 接下来需要补齐的数据

现有原型主要适合可信用户、单进程演示。它还缺少整项目依赖上传、多用户隔离、持久化任务队列和完整 PDF/OCR 输入。表格自动重算也依赖一个前提：数据行正确、合计行错误。如果源数据本身错了，算出一个自洽合计反而可能掩盖问题。

下一步应先建立有再分发授权、人工标注过的样本集，分别记录语法问题召回率、候选的语义正确率、误改率和人工介入比例。当前运行时不读取 Skill 正文，单纯删除 `SKILL.md` 不能构成有无 Skills 的有效对照。需要先接入可记录加载与工具调用的宿主，固定模型、工具权限和重试预算，再改变是否提供 Skill 指令，并增加“仅检查器、无模型”组。图像证据接入之后，还要验证候选与原始区域是否对应。没有这些数据之前，我们只报告工程测试和单次演示结果。

这次参赛让我们把“模型给出了一个答案”落实成可检查的软件行为：失败要显式呈现，候选要保留来源，采用要经过审阅。TeXada 的下一步工作也将围绕这些可以实际检验的环节展开。
