# 从候选到确认：用 Agent Skills 组织 LaTeX 修复

投稿方向：第三届 NVIDIA DGX Spark Hackathon · Agent Skills

[项目代码](https://github.com/CacinieP/TeXada-Studio-with-agentskills) · [技术报告](skills-technical-report.md) · [复现案例](casebook.md) · [演示视频](https://www.bilibili.com/video/BV16Kan6rEGv/)

微信公众号：[阅读已发布文章](https://mp.weixin.qq.com/s/kDkmQp12pBSPkqw2UpeLXw)。

一份数学讲义，漏掉分式外层的一半括号，就无法编译。另一份讲义把积分结果写错，却能生成漂亮的 PDF。写 LaTeX 时，这两类问题经常混在一起：我们既想尽快修好排版，也需要知道修复有没有改变原意。

TeXada 把源码、问题位置、候选 diff 和预览放进同一个工作台。工具检查自己能判断的部分，模型提出文本候选，使用者看过改动后采用。我们最关心的是这几步之间的交接，尤其是失败时留下什么、下一步由谁决定。

## 先从一处缺失定界符开始

样本 `math-delimiters.tex` 约定括号包住整个分式，且 x 不等于1。第20行写成了：

```latex
$\displaystyle f(x)=\left(\frac{x^2-1}{x-1}$.
```

Studio 将问题定位到这一行。语法检查返回可重试状态，编译器报告定界符缺失。本次本地文本模型的一次请求给出了候选：

```diff
-\displaystyle f(x)=\left(\frac{x^2-1}{x-1}
+\displaystyle f(x)=\left(\frac{x^2-1}{x-1}\right)
```

候选通过回判，整篇文档编译成功。在 Monaco diff 中，改动只有末尾的 `\right)`，分子、分母和原文条件都保留。使用者核对括号范围，点击采用，再下载 PDF、源码和质检报告。[完整操作及事件](dynamic-demo.md)

这个例子给了修复一个清楚的目标：补齐原文已经声明的结构。缺失下标 `a_` 就棘手得多，补成 `a_1` 虽然能解析，数字1却可能没有依据。我们的一次试卷运行中，模型连续返回 `a_{}`，两次均被检查器拒绝；即使其他括号和合计已修复，文档仍编译失败。失败候选留在[历史记录](evaluation-results/studio-earlier/README.md)中。

另一份样本将 `\int_0^1 x\,dx` 写成1，解析和编译都通过，正确值却是二分之一。这明确了当前分工：系统辅助语法和简单合计检查，数学含义由人结合上下文判断。公式提取目前限于同一行的 `$...$`；多行环境和引用需另查。样本库会同时展示抽取数与问题数。

## Skill 要真正进入请求

仓库用 `SKILL.md`、脚本和案例组织检查知识。公式 Skill 写明输入、检查状态与处理步骤，脚本执行确定性检查。这个目录结构遵循 [Agent Skills 规范](https://agentskills.io/specification)。

选择这种组织方式，是为了让一类任务的指令、工具和案例能一起维护。比如，增加一条“检查完整公式”的约定，就能找到对应的解析脚本和 `x+` 回归案例；调整检查规则时，也能同时核对说明与程序行为。任务包集中描述这些约定，宿主负责把它们接进实际工作流。

接入时有一个容易忽略的问题：把文件放进 `skills/`，执行程序未必会读取它。TeXada 为公式请求增加了明确的加载入口。宿主只允许加载 `doc-formula-verify`，检查名称和路径，再把完整 Skill 内容加入系统消息。待修公式作为单独的用户数据发送。记录中的 Skill 和提示哈希可以对应到实际请求。

Python 继续负责挑选节点、调用检查器和限制最多两次尝试，模型返回候选。只有公式 Skill 接入这个指令宿主；表格、报告和部署等技能包按各自入口使用。这样，`on` 与 `off` 的区别也可以测试：保持模型、基础提示、工具与输出上限相同，只改变是否提供 Skill 内容。

## 让状态决定下一步

缺依赖、检查器崩溃和公式写错需要不同处理。若都被归为“公式错误”，程序就可能不断请求模型，得到无助于修复环境的回答。我们让包装器同时核对 JSON 状态和退出码：

| 检查结果 | 下一步 |
| --- | --- |
| `OK` | 保留原文，或把通过回判的候选交给审阅 |
| `RETRY` | 请求候选并回判，最多两次 |
| `NEEDS_ENV` | 保留原文，停止模型尝试，处理环境 |
| `NEEDS_HUMAN` | 列出输入协议或人工处理事项 |

简单表格则直接计算。`report-01.tex` 把45与60的合计写成115，规则算得105，模型请求数为0。百分比、会计括号或模糊布局超出当前格式范围时，系统列为人工项。重算的前提是数据行本身可靠。

固定两次尝试让预算和失败路径容易检查，但当前第二次仍发送原公式，没有反馈上次候选的错误。这是一个具体的改进方向：在相同预算下加入回判反馈，观察是否减少重复候选和误改。

## 反例推动了哪些代码改动

27个合成检查案例围绕输入契约和已发现缺陷建立。其中三个问题改变了实现：

| 反例 | 原因与修正 |
| --- | --- |
| `x+` 被当作 `x` 接受 | 解析器可能只消费前缀。先核对定界符，再严格解析完整输入；F04 回归此行为。 |
| 合计是横杠，却显示已修复 | 候选计算与源码替换没有核对实际改动。现在保留原文、零编辑并列为人工项；S05 覆盖。 |
| 大整数合计少1仍被接受 | Decimal 默认精度也会舍入。现在按输入位数设置精度；T16/T17 区分正确合计和少1。 |

案例运行器保存输入、响应、退出码和脚本摘要，方便从失败追到实现。27例目前都符合预期。它们用于回归已定义行为，模型效果由另一套实验记录。

在 Python 3.11+ 虚拟环境中，从仓库根目录运行以下命令即可查看这些结果，无需 GPU：

```bash
python -m pip install -r harness/requirements.txt
python scripts/evaluate_cases.py --outdir state/article-checks-01
PYTHONPATH=harness python -m docforensics run samples \
  --state state/article-cli-01 --fixture-repairs samples/fixture_repairs.json
```

第一份报告核对27例检查结果；第二份使用预设候选演示 CLI，预期7个 `OK`、1个人工项。再次执行相同 CLI 命令应跳过8个匹配节点。报告和事件都在指定状态目录，更多步骤见[案例手册](casebook.md)。

## 保存过程，才能解释结果

只保存最终候选，会丢掉前面被拒绝的回答和失败原因。TeXada 逐次记录原检查、请求、候选和回判；超时也计入 HTTP 尝试数。报告里的“接受”指检查器接受，使用者采用仍是独立操作。

CLI 续跑时检查输入与执行上下文哈希。公式、已有裁剪文件、模型参数、Skill、检查器或依赖变化后重新检查；暂时故障在恢复后重试。每轮报告单独统计，复用项标明来源。Studio 保存完成结果和事件，重启后可按任务 ID 读取；中断任务需要新建。

界面也要保持对应关系。文档切换时清理旧 diff、忽略过期异步结果，避免用户看着新文件采用旧候选。每个任务独立保存前后编译产物。点击采用只更新编辑器，导出才保留这份修改。

## 从一份样本开始复现

仓库提供[13份 Studio 样本](../samples/README.md)。先打开正常讲义 `math-clean.tex` 确认编辑和预览，再用 `math-delimiters.tex` 观察问题定位、候选 diff 和人工采用；切换到 `report-01.tex`，还可以查看不调用模型的合计重算。每份样本对应的操作与预期现象都列在[案例手册](casebook.md)中。

样本也能用来核对编译行为。[编译复现命令](evaluation-results/studio-latex/README.md)会分别运行原稿和作者提供的参考修订，保存源码副本、日志与 PDF，便于比较修改前后的具体差异。要复现模型生成候选的过程，可按 [README](../README.md#3-接入真实模型) 配置本机模型，再对照[实机演示](dynamic-demo.md)操作。

修改一条 Skill 指令后，可以检查请求记录中的 Skill 摘要；修改检查器后，可以运行对应案例。CLI 还会在输入或执行上下文变化时重新检查。这样，读者既能试用修复流程，也能沿着指令、代码和记录继续开发。

[Skill 技术报告](skills-technical-report.md)说明职责划分、加载方式和扩展入口；同模型有无 Skill 的对照配置、逐次候选与现有结果集中在[实验报告](skills-pilot-analysis.md)。后续开发与评测安排见[路线图](roadmap.md)。
