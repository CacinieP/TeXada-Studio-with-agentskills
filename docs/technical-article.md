# 从候选到确认：用 Agent Skills 组织 LaTeX 修复

作者：LinguistsWantTech 团队；队长邓一纯，队员刘丰华。

项目：TeXada Studio with Agent Skills
投稿方向：第三届 NVIDIA DGX Spark Hackathon · Agent Skills
[项目代码](https://github.com/CacinieP/TeXada-Studio-with-agentskills) · [技术报告](skills-technical-report.md) · [复现案例](casebook.md)

一份 LaTeX 报表能够编译成 PDF，不代表里面的数字正确。TeXada 的合成报表中，两行利润分别是45和60，合计却写成115。排版引擎会忠实地把115印在页面上。另一份样本的公式下标 `a_` 不完整；模型即使补成 `a_1`，检查器也无法知道原作者想写的是1、n，还是另一个符号。

前者可以按明确规则计算，后者需要原始依据和人的判断。TeXada 因此把检查、候选生成和采用分成不同步骤：规则回答自己能够验证的问题，模型提出文本候选，界面展示差异，使用者决定是否采用。本文介绍这条工作流的实现，以及我们如何用失败案例检验它。

## 一个错误合计，怎样走到人工确认

打开仓库中的 `report-01.tex`，源码包含以下数据：

```latex
Q1 & 300 & 45 \\
Q2 & 350 & 60 \\
合计 & 650 & 115 \\
```

Studio 读取当前源码，提取支持范围内的行内公式和简单 `tabular`。表格检查识别表头、两行数据和末行合计，按列计算650与105。营收列一致，利润列不一致，因此只为利润合计生成候选：

```diff
-合计 & 650 & 115 \\
+合计 & 650 & 105 \\
```

这个步骤使用 Decimal 和明确的表格规则，不需要向模型提问。修复任务分别编译原文与候选；在已有实机演示中，两份都编译通过，恰好说明编译无法发现这个数值错误。界面将修改放入 diff，报告记录原文和候选的内容摘要、修改位置与编译结果。使用者核对数据行后，才决定是否采用。[样本与操作步骤](casebook.md)

这里有两个值得保留的边界。首先，重新求和只证明数据行与合计自洽，不能证明45和60本身正确。其次，“采用”改变的是浏览器编辑器，使用者仍需导出保留；编译结果供审阅参考，并不是阻止采用的硬性门槛。

对于 `a_`，流程在候选生成处发生变化：语法检查返回可重试状态，配置的本地文本模型提出候选，检查器再次解析候选。即使 `a_1` 被接受，也只能说明语法可解析；缺失下标的原意仍留给使用者核对。这使规则重算与模型猜测可以出现在同一界面，同时保留不同的依据。

## Skills 把步骤写成可执行的约定

仓库以 `SKILL.md`、脚本和案例组织专业步骤。公式 Skill 说明输入、检查状态和最多两次候选尝试；表格 Skill 说明支持的数字格式、合计前提与人工处理边界；报告 Skill 说明如何呈现差异与缺失证据。Agent Skills 的目录和元数据约定让这些知识可以随工具一起分发。[Agent Skills 规范](https://agentskills.io/specification)

执行端仍由 Python 编排：CLI 读取已有 `layout.json`，Studio 处理单个 `.tex`，两者按约定调用检查工具。现在，真实公式模型请求会由白名单宿主读取并验证公式 Skill 的正文，将它实际加入系统消息。请求记录保存 Skill 正文和最终提示的哈希，让“使用了 Skill”能够对应到可检查的输入，而不是仅凭目录名称判断。

这个接入也让对照有了具体含义：on 模式加载上述正文，off 模式保留相同基础提示、模型、检查器和候选预算，只去掉 Skill 指令。两种模式仍按同一流程执行工具。当前只有公式 Skill 接入这一指令宿主；其他技能包提供各自的工具或操作约定，不能一并描述为自主规划能力。正文进入请求说明机制已经接通，是否改善输出仍需实验和人工判断。

工程设计因此集中在三处：把检查器故障与文档错误分开；保存所有候选和检查结果，把采用作为独立的人工操作；让样本来源、运行上下文与结论能够相互对应。它们都能通过代码和记录核对，适合被其他文档修复工具复用。

## 状态决定下一步可以做什么

如果依赖缺失被归类为公式错误，系统可能反复向模型请求毫无帮助的修改。如果坏回包被当作通过，使用者又会看到错误的绿色结果。公式检查因此同时核对 JSON 状态和进程退出码，并规定后续动作：

| 状态 | 判断 | 后续动作 |
| --- | --- | --- |
| `OK` | 支持范围内的语法可解析 | 保留原文，或将通过回判的候选交给审阅 |
| `RETRY` | 语法失败，可以尝试文本候选 | 请求配置提供方，最多两次，再回判 |
| `NEEDS_ENV` | 检查器缺依赖、超时、崩溃或协议异常 | 保留原文，停止模型尝试，先处理环境 |
| `NEEDS_HUMAN` | 输入契约错误或无法自动解决 | 保留原文，说明需要处理的事项 |

表格有自己的输入契约：CLI 检查结构化网格，Studio 解析严格限定的简单 LaTeX 表格。遇到百分比、会计括号、单位或模糊布局，Studio 保守地转人工，避免从单元格中取出第一个数字就计算。代价是自动处理范围有限；获得的是更明确的行为边界。

最多两次尝试也有取舍：执行路径容易复现，调用有上限，但复杂错误可能无法解决。当前第二次仍基于原公式，没有反馈第一次候选的失败原因。这是后续可以单独验证的改进点，不能将“重试两次”描述成已经具备反思能力。

## 反例比一个总通过率更能解释系统

现有27例合成检查分为24个契约例和3个语义边界例。它们围绕具体要求和已知缺陷构造，适合做回归，不能据此估计陌生文档上的准确率。下面四类反例决定了实现中的关键检查。

| 输入或故障 | 容易出现的错误结论 | 当前行为与证据 |
| --- | --- | --- |
| `x+` | 只解析前缀 `x` 就认为通过 | 严格解析返回 `RETRY`；F04 |
| `1+1=3` | 语法通过就代表等式成立 | 仍是语法 `OK`，保留为明确的语义反例；F08 |
| 合计单元格为横杠 | 没改源码，却在报告里写“已修复” | Studio 转人工、零编辑，原文不变；S05与Web回归 |
| 大整数合计少1 | 使用 Decimal 就一定不会舍入 | 按输入位数设置精度；T16/T17分别检验正确与错误合计 |

`x+` 揭示了解析器使用方式的重要性。默认解析可能接受一部分输入；严格检查解决这一风险时，又需要兼顾合法的 `\left` 和 `\right` 尺寸命令。我们先检查原始定界符，再去掉尺寸命令进行完整解析，保留对应正反例。SymPy 自身也将 LaTeX 解析列为实验性功能，因此仍不能用它代替完整 TeX 编译。[SymPy 解析文档](https://docs.sympy.org/latest/modules/parsing.html)

大整数案例则说明，选对数据类型之后仍要检查计算配置。默认 Decimal 精度为28位时，`10000000000000000000000000000 + 1` 的最低位可能被舍掉。当前实现为给定十进制输入设置足够精度，检查器能够区分正确合计与少1的合计。可复现的原始响应、退出码和脚本摘要随[案例结果](evaluation-results/checker-report.json)提供。

27例均符合各自预期，是这些已定义行为的验收结果。它既没有调用模型，也没有包含独立抽取的真实 OCR 留出集；因此我们把它与实机演示、模型候选和人工判断分别报告。

## 让使用者能够审阅这些判断

Monaco 在这里承担源码编辑和差异审阅。生成候选后，原文保持可见；采用动作由使用者触发。报告把修改前后文本、行号、内容 SHA256、编译结果与剩余问题放在一起。哈希标识处理了哪一份内容，不替内容背书。

只保存最终通过的候选仍然不够。同一公式可能先收到一个被拒绝的回答，再得到语法可接受的文本；如果报告只留下后者，就无法看出重试的成本与失败原因。当前管线逐次记录原始检查、提供方请求、候选回判及接受或拒绝。提供方无有效候选时也保留失败分类，原始候选响应有长度上限并注明截断。这里的“接受”始终指检查器接受，不是使用者已经采用。

续跑也需要确认处理的是同一份内容。CLI 将终态绑定到节点输入和执行上下文两个哈希；公式或 crop 字节改变，或模型参数、Skill 正文、检查器及依赖改变，都会重新检查。暂时性服务或检查器故障不复用，恢复后可在原状态目录重试。报告只统计当前运行，复用项标明来源，历史模型请求不会混入本轮计数。这样，修复前后的比较才有明确对象。

Studio 保存完成结果与逐候选事件，服务重启后可按已知任务 ID 读取完成结果。执行中断则明确提示新建任务，不自动继续模型请求，也不恢复浏览器中未导出的编辑。它仍要求单 worker，持久化结果没有将系统变成多用户任务队列。

为使审阅入口稳定，编辑器资源固定在仓库并由本站提供，保留上游 MIT 许可。文档切换会释放旧 diff 状态并拦截过期异步结果，任务失败后恢复操作控件。这些实现服务于同一个目的：让界面展示的内容与正在审阅的候选对应。资源和部署细节见[架构说明](architecture.md)。

## 实机证据与适用范围

录屏版本在 ARM64 Spark 节点完成两次任务，GPU 查询为 NVIDIA GB10，配置模型标签为 `qwen3.8:27b-q4_K_M`，模型请求只有文本。报表完成115→105的规则候选；试卷完成公式候选与另一处合计修改，并记录修复前编译失败、候选编译通过。两次任务总耗时分别为6.94秒和105.73秒，包含前后编译和检查，且运行前已有彩排；它们不能作为稳定性能或硬件对照结果。[版本与验证条件](validation.md)

当前适用范围是可信用户的单进程实验。输入为单个 `.tex` 或已有结构树，尚无自动 PDF/OCR、多用户隔离或中断任务的自动续跑。公式抽取仍是逐行美元正则，注释或原样环境中的相似文本也可能成为候选；表格仅覆盖简单格式。依赖安装、模型准备与首次 TeX 包下载也可能需要网络。

## 把工程回归推进到可复核的对照

为了让研究不止停留在自建回归上，我们准备了一个来自开放教材《Active Calculus Single Variable》第二版的先导集合：保留6条原文公式，另为每条生成一个明确标注的注入版本，共12条。注入操作仅为移除末尾闭合花括号或添加末尾加号，来源版本、公式位置、原始文件字节哈希和改动都有记录。摘录及其修改沿用教材的 CC-BY-SA-4.0 许可。[来源与修改说明](../samples/research/ACTIVE_CALCULUS_NOTICE.md)

这仍是单一教材早期章节的小规模便利样本。六条原文不被预设为有错；另外六条也不能称为自然发生的 OCR 错误。它适合检验来源追踪、原文保留、错误注入和逐候选证据能否连接起来，不能替代独立收集的真实错误集合。

研究设三组：仅使用检查器、同一模型不提供 Skill、同一模型提供 Skill。三组共享输入和检查器；两个模型组固定模型、采样参数及每例最多两次候选预算，并轮换各例的执行顺序。只有原始检查返回可重试状态才请求模型，参考公式与错误标签不进入提示。这样既能观察候选，也能保留“初检通过后没有请求模型”的原文对照，避免把无须修改的输入强行改写。[三组协议与复现方法](../samples/research/README.md)

这次运行保留了全部36条分组结果与17次HTTP请求尝试。两个模型组各有5个候选被语法检查接受，最终拟交付文本没有组间差异。Skill组有一次请求超时；教材的一条连等式及其注入变体也未得到最终可接受的修复。这些失败都留在记录里，没有通过重新挑选样本或丢弃超时提高表面结果。当前观察没有提供Skill提升输出质量的证据；正文增加的输入token也需要单独计入成本。

原始过程与阶段解释分别见[运行记录](evaluation-results/skills-pilot/report.md)和[先导实验分析](skills-pilot-analysis.md)。独立人工复核仍待完成，因此本文不报告语义准确率或 Skill 有效提升。复核表隐藏分组，并将判定绑定到原文与拟交付文本的哈希；无法判断的项保留不确定状态。后续需要扩展来源，按文档划分开发与评测集合，再检查候选是否修复了原问题、是否引入新错误，以及人工实际投入。没有人工从零修复的对照，仅凭审阅计时也不能宣称节省时间。

TeXada 的实现让每一个通过、失败和修改对应到明确的检查范围与证据。后续更换模型或增加 OCR 时，仍可以沿这条流程判断：工具检查了什么，候选改变了什么，最后还需要人确认什么。
