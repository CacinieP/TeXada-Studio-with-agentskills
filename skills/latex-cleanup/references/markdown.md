# Markdown 专属规则

## 先确认方言

从项目配置、相邻文档和现有 VS Code 预览插件判断使用 CommonMark、GFM、Pandoc、Quarto
或其他扩展。普通 Markdown 解析器可接受的文档不一定符合目标渲染器。
MDX / Quarto 等超出 `.md` 基础支持的内容按项目工具处理，不作为普通 Markdown 全文重写。

## 保护区域

- 保留 fenced / indented code block、行内代码及多行 code span 的原文、语言标记和空格。
  围栏可能是反引号或波浪线，长度不一定为三个，也可能嵌套在列表或引用中。
- 保留 YAML front matter，尤其 `|` / `>` 标量、缩进和日期字符串。不要自动重排键或转换类型。
- 保留内联 HTML、注释、原始块以及链接定义的标识符和目标。
- 保护行内/块级数学公式的命令、转义、上下标及换行。`$` 也可能表示货币，
  不用计数美元符号的方式判定公式错误。
- 保留脚注、任务列表、引用块、表格和项目扩展语法。未识别的区域保持原文并说明。

## 格式清洗

- 行尾两个或更多空格可能表示硬换行；末尾反斜杠也可能表示硬换行。不要全局 trim。
- 不因“空行过多”而删除段落边界，或改变列表的松散/紧凑结构。
- 不统一全文件缩进；嵌套列表和缩进代码块对缩进敏感。
- 标题级别、标题文字、显式 ID 及链接锚点的改变属于结构编辑，必须追踪站内引用。
- 不全局进行全角/半角、智能引号、中英文空格或标点替换。需要时只处理已确认的普通正文，
  排除代码、公式、URL、标识符和专有名称。
- 若采用 markdownlint 或 Prettier，沿用项目配置，先查看拟修改差异。
  不将所有 lint 警告直接等同于错误，不自动改变公式定界符或扩展语法。

## 修复和验收

只在证据明确时修复围栏、列表或链接；渲染器通常会接受未闭合围栏，这可能是合法的文件末尾代码块，
也可能是错误，需要结合内容判断。资源路径相对于实际文档/站点根目录解析，不能随便换成绝对路径。
不把无法联网验证的远程链接标为已失效。

检查差异中所有代码、公式、链接目标、front matter 和硬换行；在目标 VS Code 预览下检查
段落、列表、表格和公式。AST 或 HTML 对比可作为证据，但不是所有方言下的完整语义证明。
无对应预览器时说明只做了源码检查。

参考：[CommonMark 规范](https://spec.commonmark.org/0.31.2/)、
[VS Code Markdown](https://code.visualstudio.com/docs/languages/markdown)。
